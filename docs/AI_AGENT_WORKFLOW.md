# 用 GPT 和备用 agent 修改板牙考研

目标是让你用自然语言提需求，不必操作终端或 SSH；每个改动只处理一件事，完成后有测试和可查看的 PR。

## 平时：在 GPT 项目里提需求

在板牙考研的 GPT 项目中新开一段对话，直接描述科目、日期、要改的任务和希望保留的记录，例如：

> 把英语二 10 月 20 日的翻译练习改到 10 月 22 日，保留原有错题和打卡；先检查最新项目，再完成必要改动和测试。

执行者先读最新 `main`、`AGENTS.md`、[文档索引](index.md)、[项目状态](PROJECT_STATUS.md)和[开发流程](WORKFLOW.md)，再检查相关科目、开放 PR 与测试结果。一个需求建一个分支和 PR；不覆盖其他分支，也不把真实学习记录写入仓库。

个人任务调整和公开默认计划是两回事。个人修改应保存在 PWA 的本机记录和已启用的云快照里；只有明确要改所有用户共用的默认计划时，才改公开计划文件。普通 GPT 对话目前不能读取服务器私人快照；若要让 GPT 根据实际错题或完成情况分析，需要先在项目中实现并验证受限、可撤销的只读授权。当前可以在 PWA 设置中复制一段记录，再自行决定是否粘贴给对话。

## 急用时：让 API agent 做同一项目的代码 PR

额度不够时，可以把**公开的 `kopdabanya-commits/BanyaKaoyan` 仓库**连接到你信任的 API agent。只给它访问这个仓库和创建分支、提交、开 PR 的权限。优先用可撤销、仅限此仓库的 GitHub App 授权；若服务只支持访问令牌，则只授予仓库内容读写和 PR 读写。Actions 只需读取状态时给只读权限。

备用 agent 只处理代码和技术文档。不要给仓库管理员权限、Actions 写入权限、组织范围权限、服务器 SSH、生产 API 密钥、同步密钥或真实学习备份。代码 PR 经 CI 验证后，现有 GitHub 发布流程会在合并到 `main` 时发布现有 PWA；因此备用 agent 不要合并、直接推送 `main` 或手工部署服务器。需要服务器工作时，把必要代码和部署步骤放进 PR，由已授权的项目维护流程执行并验证。

给备用 agent 的任务提示词可以直接复制并补上最后一行：

```text
你协助维护公开 GitHub 仓库 kopdabanya-commits/BanyaKaoyan，这是同一个 PWA 中的英语二和政治两个科目。请先读最新 main、AGENTS.md、docs/index.md、docs/PROJECT_STATUS.md、docs/WORKFLOW.md 和相关待办/架构文档，查看开放 PR，再只处理下面这一项：

【在这里写清楚一个需求、科目和日期】

保持同一个 PWA、仓库和现有发布入口；遵守 AGENTS.md。保护现有学习数据，不改用户未要求的计划，不提交个人记录、备份、令牌、服务器密码或密钥。不要覆盖别的分支，不直接推送 main，不合并，不部署。只读相关文件，不扫描无关仓库或寻找秘密。

完成后运行与改动匹配的检查，更新公开项目状态/待办文档，创建一个短分支和 PR。PR 说明改了什么、跑了哪些检查、CI/发布还需谁完成；如遇冲突或缺少授权，说明具体阻塞，不猜测、不伪称完成。
```

## 保持省时

- 一次对话或一个备用 agent 只做一个清楚的需求；另一个 agent 正在改同一功能时先等它开 PR，避免同时改同一文件。
- 要求它只读相关文件、跑项目已有测试，并在 PR 里给短报告；不要让它复述整段聊天或输出大段构建日志。
- 合并前看 PR 的变更摘要和 CI。合并会触发现有发布工作流；之后仍要分别报告自动化检查、真实服务器检查和手机验收。
- 只需要改自己的一个日期或任务时，优先在 PWA 任务记录页操作；这比改公开模板更快，也不会把私人内容放进 GitHub。

仓库当前是公开的；连接 agent 等于允许该服务读取公开源代码和技术文档，但不应让它接触你的私人学习数据或服务器凭据。公开仓库无法靠隐藏链接变成不可搜索。
